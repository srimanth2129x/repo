4.1 One-file vs one-folder build

The spec does not mandate --onefile or --onedir.

Choose whichever is more reliable for this Sensor, and explain the decision in the final report.

Note the trade-off explicitly:

--onefile produces a single clean executable, but extracts to a temporary directory at runtime that is deleted on exit. This creates real failure modes for persistent runtime data (see Section 6).
--onedir produces a folder rather than a single file, but is easier to debug and avoids the temp-extraction problem.

Reliability matters more than looking clean. If --onefile introduces risk to device identity or checkpoint persistence, prefer --onedir.

6. RUNTIME DATA FILE LOCATION — CRITICAL

The Sensor writes persistent runtime data, including files such as:

data/sensor_device.json data/sensor_checkpoint.json data/sensor_offline_queue.json

This is the single most likely thing to silently break under PyInstaller packaging.

Under a --onefile build, PyInstaller extracts the application to a temporary directory (sys._MEIPASS) that is deleted when the process exits. If the Sensor writes runtime data relative to the script/bundle location, then:

the device ID is regenerated on every run,
the checkpoint is lost on every run,
the offline queue is destroyed on every run,
the Sensor re-reads and re-sends historical events, flooding the server.
Requirements
Runtime data MUST be written to a persistent, writable location.
Acceptable locations:
The directory containing the executable, resolved from sys.executable (NOT __file__, NOT sys._MEIPASS), or
A per-user application data directory such as %LOCALAPPDATA%\SentinelTwin\.
Runtime data MUST NEVER be written to sys._MEIPASS or any PyInstaller temp extraction path.
Do NOT assume the executable's directory is always writable. If it is not, fall back to the per-user application data directory and log which location is being used.
If the runtime data directory changes from the current behavior, handle migration of any existing data safely, and verify compatibility with the existing checkpoint logic. Do not silently change checkpoint locations in a way that could cause event loss or duplicate event floods.

Explicitly confirm in the final report where runtime data is written, and how this was verified.
